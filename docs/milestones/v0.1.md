# v0.1: first test report to first verdict

**Goal**: a team can send e2e results from their CI with one command, gate a promotion on the
verdict with another, and see, for each component and environment, which version was last tested
and whether it passed. One instance serves several projects, and one person can follow all of theirs.

## User story

> As a developer, I add one step after my Playwright tests in CI. It sends the CTRF report to
> Kollaudo with the component, environment and version. I open Kollaudo and see a matrix of my
> components and environments, with the latest tested version and its results in each cell.
>
> Before promoting to production, my pipeline runs `kollaudo verdict` on staging. It stops if the
> tests failed, and also if they never reported.
>
> I have several projects on the same Kollaudo, and I switch between them from the UI.

## In scope

### Server (`apps/server`)

- `docker compose up` starts Kollaudo and PostgreSQL. Migrations run on startup.
- Projects and API tokens are managed with the server's admin command
  ([ADR 0007](../adr/0007-scoped-api-tokens.md)):
  `kollaudo-server project create <name>` prints one `ingest` token and one `read` token, and
  `kollaudo-server token create | list | revoke` manages the others.
- Endpoints, all under `/v1` except the health check, authenticated with `Authorization: Bearer <token>`.
  Every token belongs to one project, so the project never appears in the path:

| Method | Path | Scope | Purpose |
|---|---|---|---|
| `GET` | `/healthz` | none | liveness |
| `POST` | `/v1/test-runs` | `ingest` | ingest a CTRF report with component, environment, version and kind |
| `GET` | `/v1/project` | `read` | the token's project, so clients can label it |
| `GET` | `/v1/test-runs` | `read` | list runs, filtered by component, environment and version |
| `GET` | `/v1/test-runs/{id}` | `read` | one run with its test results |
| `GET` | `/v1/health` | `read` | the component × environment matrix of the project |
| `GET` | `/v1/verdict` | `read` or `ingest` | the verdict of a version in an environment, with its reasons |
| `GET` | `/v1/openapi.json` | none | the OpenAPI document |

- Components, environments and versions are created on first use ([ADR 0005](../adr/0005-create-on-first-use.md)).
- The CTRF report is validated. An invalid report is rejected with a clear error listing the
  problems.
- Versions accept an optional `digest` of the built artifact, with the same conflict rule as
  `commit` ([ADR 0005](../adr/0005-create-on-first-use.md)).
- The verdict is `pass`, `fail` or `unknown` with its reasons
  ([ADR 0013](../adr/0013-verdict-pass-fail-unknown.md)), under the default policy
  ([ADR 0014](../adr/0014-policy.md)). `require` lists kinds that must have a run, and can only
  tighten the policy.

### CLI (`packages/cli`, published as `@kollaudo/cli`)

```bash
export KOLLAUDO_URL=https://kollaudo.example.com
export KOLLAUDO_TOKEN=kol_...   # an ingest token

kollaudo push ctrf-report.json --component frontend --env staging --version 1.2.0 \
  [--kind e2e] [--commit <sha>] [--branch <name>] [--tag <tag>] [--pull-request <number>] \
  [--digest <sha256:...>]

kollaudo verdict --component frontend --env staging --version 1.2.0 [--require e2e,smoke]
```

- `--kind` defaults to `e2e`. `--env` is optional: without it the run is build level
  ([ADR 0004](../adr/0004-own-internal-model.md)).
- Exit code `0` when the report is accepted, even if tests failed. Failing the pipeline on test
  results is the job of the test runner, and of `kollaudo verdict`.
- `kollaudo verdict` prints the verdict and its reasons, and exits with `0` for pass, `1` for fail,
  `2` for unknown and `3` when it couldn't get a verdict.
- `kollaudo --help`, `kollaudo push --help` and `kollaudo verdict --help` document every option.

### UI (`apps/web`)

- **Health matrix**: rows are components, columns are environments. Each cell shows the latest
  tested version, when it was tested, and passed, failed, skipped and flaky counts.
- **Test run page**: the tests of one run, grouped by suite, with failure messages, retries and a
  flaky marker.
- **Projects**: the user adds a project by pasting its `read` token. The UI stores the tokens in
  the browser, lists every project with a summary of its health, and has a project switcher.
- Uses only the public API ([ADR 0010](../adr/0010-self-hosted-api-first.md)).

### Project

- pnpm monorepo as in [ADR 0011](../adr/0011-typescript-monorepo.md), stack as in
  [ADR 0012](../adr/0012-server-stack.md).
- GitHub Actions: lint, typecheck and tests on every pull request.
- A container image published to `ghcr.io/kollaudo/kollaudo` for each release.
- Recipe: Playwright with the CTRF reporter, in GitHub Actions.
- README quick start that works end to end.

## Out of scope for v0.1

- Policy files, JUnit XML, deployments (v0.2).
- The verdict in the UI. It comes with policy files, so the UI can show the rules it applied.
- Bugs, UAT sign-offs and manual check results (v0.3).
- CDEvents, gate recipes (v0.4).
- Users, roles and single sign-on. Access is by project token only.
- An HTTP API to manage projects and tokens.
- Helm chart.

## Done when

1. `docker compose up`, then `kollaudo-server project create demo` returns an `ingest` and a
   `read` token.
2. `kollaudo push` with a real Playwright CTRF report and the `ingest` token returns `0` and a link
   to the run.
3. With the `read` token, the health matrix shows the run in the right cell, and the run page shows
   its tests.
4. `kollaudo verdict` on that version exits `0` if the run passed and `1` if it failed. On a
   version with no runs in that environment, or with `--require` naming a kind that never ran, it
   exits `2`.
5. Pushing an invalid report fails with a readable error and exit code `1`. Pushing with a `read`
   token fails with `403`.
6. A second project shows up in the UI next to the first one, and its data stays separate.
7. The same flow is covered by an automated end-to-end test in CI.

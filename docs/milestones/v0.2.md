# v0.2: into a GitOps delivery

**Goal**: a team that delivers with Argo CD and Kargo can install Kollaudo on Kubernetes, send
results from any test framework, see which version runs in each environment, and let Kargo promote
only the versions Kollaudo passed, under rules that a pipeline can't relax.

## User story

> Our platform team installs Kollaudo in the cluster with Helm, next to Argo CD and Kargo.
>
> Our CI runs unit tests that write JUnit XML, and sends them with `kollaudo push`, as it would a
> CTRF report. When Argo CD syncs a version into an environment, its notifications tell Kollaudo,
> so the matrix shows what is deployed where, next to what was tested.
>
> In Kargo, the verification of `staging` runs our e2e tests and asks Kollaudo for the verdict.
> Freight reaches `production` only when the verdict is `pass`: a failed run, tests that never
> reported, or tests of another version than the one in `staging` keep it there. The rules are kept by
> Kollaudo: removing a test step from the pipeline doesn't make the gate weaker.

## In scope

Ordered by priority: each part is useful on its own, and can be released as soon as it is done.

### 1. JUnit XML

- `kollaudo push` accepts JUnit XML as well as CTRF, recognized by its content. Several files and
  glob patterns are merged into one run, since many tools write one file per suite:

  ```bash
  kollaudo push "test-results/**/*.xml" --component api --version 3f2a9c1 --kind unit
  ```

- The CLI converts JUnit to CTRF before sending it, so the HTTP API keeps one format. An ADR records
  this choice and the mapping: suites, `failure` and `error`, `skipped`, durations, and the flaky
  reruns that tools such as Maven Surefire and pytest write.
- Tested on the JUnit files of at least Maven Surefire, pytest, Jest, Go (`go-junit-report`) and
  Azure DevOps' test tasks.

### 2. Helm chart

- A chart in `charts/kollaudo`, published with each release as an OCI artifact on
  `oci://ghcr.io/kollaudo/charts/kollaudo`.
- It runs Kollaudo against an existing PostgreSQL, read from a Secret: Kubernetes teams usually run
  databases with an operator, such as CloudNativePG, and the docs show how.
- Values for the image, the database Secret, an Ingress, resources and probes on `/healthz`.
  Admin commands run with `kubectl exec`.
- Replicas starting together take turns on the database migrations.

### 3. Deployments

The model has had deployments since [ADR 0004](../adr/0004-own-internal-model.md): v0.2 receives
and shows them.

| Method | Path | Scope | Purpose |
|---|---|---|---|
| `POST` | `/v1/deployments` | `ingest` | record that a version of a component runs in an environment |
| `GET` | `/v1/deployments` | `read` | list deployments, newest first, filtered by component and environment |

```bash
kollaudo deployed --component api --env staging --version 3f2a9c1 [--digest sha256:...]
```

- The command is named after what happened: Kollaudo records deployments, it never deploys
  ([ADR 0002](../adr/0002-judge-never-orchestrate.md)).
- Components, environments and versions are created on first use, with the same metadata rules as
  test runs ([ADR 0005](../adr/0005-create-on-first-use.md)).
- `/v1/health` adds the version deployed in each environment. The matrix shows it in each cell, and
  marks the cells where the latest tested version is not the deployed one.
- The verdict reports the version deployed in the environment. Requiring it is a rule of part 4.

### 4. Rules kept by Kollaudo, and overrides

Moved here from v0.3: until rules are kept by the server, the pipeline that asks for a verdict also
decides which tests it needs, and a pipeline that loses a test step loses it from the gate too.

- Rules for each component and environment, kept and versioned by Kollaudo, and changed only with a
  token of their own: which kinds of test are required, and whether the tested version must be the
  one that runs in the environment. A request can make them stricter, never weaker
  ([ADR 0014](../adr/0014-policy.md)).
- An override for urgent fixes: who, why and until when, recorded and shown in the verdict.
- Deployments to an environment without a `pass` before them are marked, so that a gate that was
  skipped is visible.
- What to do when Kollaudo can't be reached, recommended for each kind of environment.

ADRs come first, for the format of the rules, the override and the failure behaviour.

### 5. Recipes

| Recipe | Checked by |
|---|---|
| **Kargo**: an `AnalysisTemplate` that runs the e2e tests, sends them and gates on the verdict | a workflow that runs Kargo, Argo CD and Kollaudo (Helm chart) in kind, and checks that Freight is promoted on `pass` and stays on `fail` and `unknown` |
| **Argo CD notifications**: a webhook that sends each sync as a deployment | the same kind workflow |
| **Azure DevOps**: unit tests in JUnit, `push`, and a `verdict` step before a deployment stage | a pipeline run by hand, since Azure DevOps can't run in our CI |

The kind workflow runs weekly and on demand, not on every pull request: it takes several minutes.

## Out of scope for v0.2

- The verdict in the UI (v0.3).
- Bugs, UAT sign-offs and manual check results (v0.4).
- CDEvents, gate recipes for other tools, a GitHub Action (later).
- A Backstage plugin ([roadmap](../../README.md#roadmap)).
- Users, roles and single sign-on.

## Done when

1. `helm install` with a PostgreSQL Secret starts Kollaudo, and `kubectl exec … project create`
   returns its tokens.
2. `kollaudo push` with the JUnit files of each listed tool stores runs with the right counts,
   suites and failure messages.
3. An Argo CD sync shows up as a deployment, and the matrix shows the deployed version next to the
   tested one.
4. A rule that requires e2e tests holds when the pipeline doesn't ask for them, and a verdict on a
   version that doesn't run in the environment fails when the rule requires it. An override lets a
   version through, and the verdict says who allowed it and why.
5. In kind, Kargo promotes Freight to the next stage when the verdict is `pass`, and doesn't when it
   is `fail` or `unknown`.
6. The Azure DevOps recipe has been run once on a real pipeline.
7. Every part is in the CHANGELOG and released with the release workflow.

# v0.4: a gate in one line

**Goal**: a team that deploys with GitHub Actions can gate a deployment on Kollaudo's verdict with one
step, and send its test results with another, without installing Node.js or learning the CLI. A team
on Azure DevOps has a recipe tried on a real pipeline.

## User story

> Our deployment workflow on GitHub Actions has a `production` job. Before it deploys, one step asks
> Kollaudo whether the version passed in `staging`:
>
> ```yaml
> - uses: kollaudo/action@v0
>   with:
>     url: ${{ vars.KOLLAUDO_URL }}
>     token: ${{ secrets.KOLLAUDO_GATE_TOKEN }}
>     component: api
>     environment: staging
> ```
>
> On `pass` the job goes on. On `fail` or `unknown` it stops, and the summary of the run says why,
> with a link to each test run, as `kollaudo verdict` does. If Kollaudo doesn't answer, it stops too.
> The version defaults to the commit of the workflow, the one our CI sent its results with.

## In scope

Ordered by priority: each part is useful on its own.

### 1. A GitHub Action for the gate

- **Where it lives** is decided by an ADR before any code: the GitHub Marketplace lists only actions
  whose `action.yml` is at the root of their own public repository. The proposal is a repository
  `kollaudo/action`, whose root action is the gate, with `kollaudo/action/push@v0` next to it for
  test results. Tags follow the releases of Kollaudo (`v0.4.0`), with a moving major tag (`v0`).
- **How it runs**: a composite action that runs `npx @kollaudo/cli` at the version of the action's
  release, on the runner's Node.js. No JavaScript bundle to build and review, and the same code as
  the CLI, already tested.
- **Inputs**: `url`, `token`, `component`, `environment`, `version` (default: `github.sha`) and
  `require`.
- **Outcomes**, as in [ADR 0019](../adr/0019-when-the-gate-is-skipped-or-kollaudo-is-down.md): the step
  fails on `fail`, `unknown` and no answer. Letting `unknown` or no answer through, for development
  and preview environments, is an explicit input, `allow: unknown` or `allow: unknown,no-verdict`,
  never the default.
- **Outputs**: `outcome` and `message`, so later steps can use them.
- **Job summary**: the verdict, its reasons and links to the test runs, written to the summary of
  the workflow run, where people look first when a deployment stops.
- It needs the verdict as JSON from the CLI: `kollaudo verdict --json`, a
  [good first issue](https://github.com/kollaudo/kollaudo/issues/54) open now.

### 2. A GitHub Action to send results

- `kollaudo/action/push@v0`: `kollaudo push` with the same inputs as the CLI, `path` for the report
  files (CTRF or JUnit XML, with glob patterns), and `if: ${{ !cancelled() }}` shown in every
  example, so that failed tests are sent too.
- The Playwright and pytest recipes show the actions, and keep the CLI as the alternative for any
  other CI.

### 3. Azure DevOps

- A recipe with unit tests in JUnit, `push`, `deployed` and a `verdict` step before a deployment
  stage. It can't run in our CI, so it is published once it has run on a real pipeline, on a personal
  Azure DevOps organization. It needs nothing that 0.3.0 doesn't have.

## How the actions are tested

| Action | Checked by |
|---|---|
| Gate | a workflow that runs Kollaudo from its image as a service container, sends results, and checks that the step passes on `pass`, fails on `fail` and `unknown`, fails when Kollaudo is down, and lets `unknown` through only with `allow` |
| Push | the same workflow: it sends a CTRF report and a JUnit report, then asks for the verdict |

The workflow runs on every pull request of the action's repository, and against each release of
Kollaudo.

## Out of scope for v0.4

- Bugs, UAT sign-offs and manual check results (v0.5).
- GitHub deployment protection rules, which need a GitHub App, and CDEvents (later).
- A Backstage plugin ([roadmap](../../README.md#roadmap)).
- Users, roles and single sign-on.

## Done when

1. A workflow on GitHub Actions gates a job on the verdict with one step, and the step passes on
   `pass` and fails on `fail`, `unknown` and no answer.
2. The summary of a run that stopped says why, with links to the test runs.
3. `allow` lets `unknown`, or no answer, through only when asked, and the summary says it did.
4. One step sends CTRF or JUnit reports, also after failed tests.
5. The actions are listed on the GitHub Marketplace, and the README's quick start shows them.
6. The Azure DevOps recipe has run on a real pipeline.
7. Every part is in the CHANGELOG and released with the release workflow.

# v0.5: evidence from people

**Goal**: what testers find and decide counts where the gate looks. A UAT sign-off or a manual check
is evidence a policy can require, sent by the person who gave it and not by the pipeline it judges.
A failed test can carry the bug it is known for, so that a `fail` says whether it is new. Both come
from the tools where testers already work, by a request those tools send: Kollaudo still needs no
credentials to them ([ADR 0006](../adr/0006-push-based-ingest.md)).

## User story

> Before a version of `checkout` reaches `production`, our product owner tries it in `staging` and
> signs it off:
>
> ```bash
> kollaudo signoff --component checkout --env staging --version 3f2a9c1 \
>   --kind uat --outcome pass --note "Checked the new payment page with the two test cards"
> ```
>
> Our policy requires `uat` in `staging`, from a sign-off. Until it comes, the verdict is `unknown`,
> and says that `uat` is waiting for a sign-off. A green report of a `uat` suite sent by CI doesn't
> replace it: CI holds no token that can sign off.
>
> When an e2e test fails, the tester who looks at it opens a bug in Jira and links it to the test.
> The next verdict still fails, but its reason says `checkout › pays with a saved card` fails with
> a known bug, `SHOP-412`, open, and lists the tests that fail with no bug linked: those are new.
>
> We don't type commands for this: a Jira automation rule sends the sign-off when the UAT ticket of
> the version moves to *Approved*, and the link when a bug is created from a failed test.

## In scope

Ordered by priority: each part is useful on its own.

### 1. Sign-offs and manual checks

- **A sign-off is a test run** of a kind, such as `uat` or `manual`, with one outcome, `pass` or
  `fail`, a note, and who gave it. It is judged like any other run: by its latest one, with
  `maxAge` and `deployed`, so a sign-off of another version, or one given before the version was
  deployed, doesn't count. Manual checks with several cases are sent as a report, CTRF or JUnit, as
  today.
- **A new token scope, `signoff`**, held by people, as `override` is
  ([ADR 0018](../adr/0018-overrides.md)): the pipeline that sends results can't sign off its own
  version. Tokens can be limited to components and environments
  ([ADR 0017](../adr/0017-trust-in-evidence.md)), and the name of the token is the author until
  Kollaudo has users.
- **A policy can require a sign-off**: `signoff: [uat]` next to `require`. A kind listed there
  counts only from a run sent with a `signoff` token. A `fail` sign-off fails the verdict; a
  sign-off can be given again, and the latest one counts.
- **API and CLI**: `POST /v1/signoffs` and `kollaudo signoff`, which also prints the verdict that
  follows. `GET /v1/signoffs` lists them. The verdict, the UI and the log of verdicts show the
  author and the note.
- An ADR records why a sign-off is a test run and not a new concept, and why it needs its own scope.

### 2. Bugs linked to failed tests

- **A link** says that a test of a component fails because of a bug: the test name, as it appears in
  the reports, a key such as `SHOP-412`, a URL, and whether the bug is `open` or `closed`. It holds
  for every version until the bug is closed, since a bug usually outlives the run that found it.
- `POST /v1/bugs` creates or updates a link, by key, with an `ingest` token: a closed bug sent again
  with its key closes the link. `kollaudo bug link` and `kollaudo bug close` do the same.
- **A known bug never changes the verdict.** A failed test with an open bug still fails the run:
  letting a version through is what an [override](../overrides.md) is for, with a reason and an
  expiry. The verdict says which failures are known and which are new, in its reasons and in
  `kollaudo verdict --json`.
- The UI shows the bug next to each failed test, and on the matrix marks the cells where every
  failure is known.

### 3. From the tools where testers work

Recipes, each published once it has run on a real instance, as the Azure DevOps recipe was:

- **Jira automation**: a rule that sends a sign-off when an issue of a UAT type moves to a status,
  and one that links a bug, and closes the link, when a bug with a failed test in a field is created
  or resolved. Both with *Send web request*, the token in a header, and the component, environment
  and version read from fields of the issue.
- **A form for people without a terminal**: a page of the docs, not of Kollaudo, that shows the
  `curl` a tester can paste, until Kollaudo has users and the UI can take a sign-off itself.

Test management tools, such as Xray, Zephyr, TestRail or Azure Test Plans, export JUnit or have
webhooks: a recipe for one of them is welcome, and is in scope if someone tries it on a real
instance.

## How it is tested

| Part | Checked by |
|---|---|
| Sign-offs | server tests: the scope, the limits of the token, `signoff` in the policy, a `fail` sign-off, a newer one replacing it, `maxAge` and `deployed`; and `e2e/run.sh`, from a sign-off to a `pass` |
| Bugs | server tests: links by key, closing, known and new failures in the reasons, and a verdict that stays `fail` |
| Recipes | a run on a real Jira Cloud site, with the requests it sent kept as fixtures for the server tests |

## Out of scope for v0.5

- Users, roles and single sign-on, and so sign-offs given in the UI.
- Reading from Jira or any other tool: Kollaudo receives, it never fetches.
- Test cases, plans and campaigns: Kollaudo is not a test management tool.
- A known bug that turns a `fail` into a `pass`.
- GitHub deployment protection rules and CDEvents (v0.6).

## Done when

1. A policy that requires a `uat` sign-off gives `unknown` until one is sent, `pass` after a `pass`
   sign-off, and `fail` after a `fail` one.
2. A `uat` run sent with an `ingest` token doesn't satisfy `signoff: [uat]`, and the verdict says why.
3. The verdict, the UI and the log show who signed off, when, and their note.
4. A failed test linked to an open bug is marked as known in the verdict, the JSON and the UI, and
   the verdict is still `fail`.
5. Closing a bug removes the mark from the next verdict.
6. The Jira recipe has run on a real site, for sign-offs and for bugs.
7. Every part is in the CHANGELOG and released with the release workflow.
